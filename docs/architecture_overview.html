9C Nebulizer 架构总览

这是一个基于 Zephyr RTOS 和 STM32G070CBT6 的眼科雾化控制器项目。整体架构不是简单的“main + loop”，而是 一个围绕 app_context、事件队列、状态机和多线程周期任务组织起来的嵌入式控制系统。

Zephyr RTOS 事件驱动状态机 多线程周期控制 板级抽象 + 驱动包装 Host / Mist 双协议链路

一句话理解

系统定位

一个“治疗流程协调器”，通过统一状态、统一事件和统一遥测对象把传感、加热、风机、雾化板和上位机串起来。

控制核心

AppTask 负责状态切换和命令裁决，ControlTask 负责周期控制输出。

数据中心

telemetry_status_t 是全局快照视图，业务模块通过 app_context 读写它。

安全策略

安全检测独立线程轮询，异常通过事件注入状态机，最终统一进入 FAULT 或 PAUSED。

分层结构

下面这层次基本对应当前工程目录和代码职责。

应用编排层 src/

负责启动顺序、状态机、事件分发、安全落锁、遥测聚合。

  • src/main.c 只做启动入口。
  • src/app/app_init.c 串起所有服务初始化和配置加载。
  • src/app/app_tasks.c 是运行期调度中心。
  • src/state_machine/treatment_sm.c 管治疗状态迁移规则。
业务服务层 services/

把加热、风机、雾化、传感、设置存储、主机通信拆成独立服务，避免业务逻辑直接碰底层驱动。

  • communication/: Host RX/TX 与命令应答。
  • heat/: PID 与 TRIAC 加热输出控制。
  • mist/: 雾化板链路和运行状态管理。
  • sensors/, fan/, storage/: 采样、执行器和配置落盘。
协议与编解码层 protocols/

把帧格式、CRC、环形解析器和 Host / Mist 协议对象化，通信服务只负责收发，不把协议细节散落到线程里。

  • common/: CRC16、frame codec、ring parser。
  • host/: 上位机协议和命令解释。
  • mist/: 雾化板协议和命令打包。
板级与设备适配层 boards/ + src/platform/ + drivers_app/

这里把 Zephyr 原生设备树、板级资源和应用驱动包装拼起来，让上层服务使用“业务友好接口”而不是直接操作设备句柄。

  • boards/arm/nebulizer_g070cbt6/: 自定义板定义。
  • src/platform/board_devices.c: 板资源映射和校验。
  • drivers_app/: GPIO / ADC / UART / PWM / TIMER 的应用侧包装。

启动链路

1

main 入口极简

main.c 只做两件事：app_init() 和 app_tasks_start()。这说明主设计思想是“初始化后完全交给任务系统”。

2

app_init 按依赖顺序拉起服务

先初始化上下文，再做关键设备检查、配置存储加载、传感/风机/加热/雾化/主机通信/安全/遥测初始化。

3

运行期依赖配置快照

配置和 PID 参数加载后会立即写回 app_context，后续线程不直接维护自己的配置副本。

线程模型

当前运行期不是一个 super loop，而是多个职责明确的 Zephyr 线程协作。

主控线程

AppTask

消费事件队列，解析 Host 命令，执行状态迁移，进入故障/恢复/暂停/完成状态，并触发状态快照上报。

20 ms

SensorTask

周期采样传感器，结果更新到 app_context 里的 sensor_snapshot_t。

20 ms

ControlTask

依据当前状态决定风机、雾化、加热输出，同时在运行态递减剩余治疗时间。

10 ms

SafetyTask

轮询安全服务，发现异常就投递 FAULT / PAUSE / RESUME 事件。

500 ms

TelemetryTask

周期发布遥测；Host 命令处理也会在关键状态变更时主动补发状态快照。

通信线程

HostRx / HostTx / MistTask

Host 收发和雾化板处理各自独立线程，避免把串口阻塞、解析和业务决策混在一起。

状态机与事件流

状态集合

  • BOOT
  • SELF_TEST
  • READY
  • CONFIGURING
  • RUNNING_HOT / RUNNING_COLD
  • PAUSED
  • DONE
  • FAULT

主要事件

  • HOST_CMD
  • START / STOP / PAUSE / RESUME
  • FAULT / FAULT_CLEAR
  • HEARTBEAT_TIMEOUT
  • MIST_STATUS
A

命令进入

上位机命令通过 Host 通信服务进入 app_handle_host_command()，先做参数检查，再决定是立即修改配置，还是投给状态机裁决。

B

状态裁决

treatment_sm_handle_event() 只负责“当前状态 + 事件 + 当前快照”能不能转移，不直接操作硬件。

C

动作执行

真正的输出动作在 app_apply_state_transition() 和 ControlTask 中完成，比如停止风机、停加热、请求停雾化等。

关键共享对象

telemetry_status_t

项目里最重要的汇总结构，包含状态、治疗配置、传感快照、雾化板状态、热控 PID、维护模式、故障码和剩余时间。

app_context

统一的状态仓库。线程之间尽量不直接交叉依赖，而是通过它交换快照和控制状态。

app_event_queue

把“命令解析”和“状态变更”解耦。通信、安全、控制等模块把事件送进队列，AppTask 集中处理。

settings_store

把治疗参数和 PID 参数持久化，并在启动时恢复，说明系统考虑了掉电后继续可用的维护需求。

我对当前架构的判断

  • 这是一个比较清晰的“分层 + 状态机 + 多线程周期任务”架构，不是把所有逻辑塞进一个控制循环。
  • 应用层和设备层的边界是明确的，drivers_app 和 services 的划分是合理的。
  • Host 命令和安全事件最终都汇总到 AppTask，这让状态一致性比较容易维护。
  • 控制输出主要在 ControlTask，状态裁决主要在 AppTask，这种“决策 / 执行分离”是当前代码最值得保留的设计点。
  • 从目录和函数职责看，当前项目已经具备继续拆出更完整架构文档的基础，比如时序图、故障树、协议图和线程优先级分析。
